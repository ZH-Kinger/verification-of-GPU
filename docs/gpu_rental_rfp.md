## 1. 采购概述

### 1.1 用途

分布式模型训练，模型类型为 **VLA（Vision-Language-Action）** 与 **world model**。

这两类负载对平台的要求与常规 LLM 训练不同，供应商在设计方案时必须考虑：

- **数据以视频 / 图像帧为主**，数据集体量大、单文件小、随机读多。存储的**元数据性能**
  和**聚合读带宽**是瓶颈，不是容量。
- **单步计算相对轻、数据吞吐相对重**，dataloader 打不满会直接拉低 GPU 利用率。
- **长序列 / 大 batch**，显存容量敏感，这是我方倾向 B300（288GB）而非 H100（80GB）的原因。
- **训练周期长**，单次训练动辄数周，因此**有效训练时间占比（Goodput）比峰值算力更重要**。

### 1.2 规模与交期

| 批次 | 规格 | 节点数 | GPU 数 | 期望交付 |
|---|---|---|---|---|
| 首批 | B300 8 卡节点（备选 H200） | 16 | 128 | **2026-10-15** |
| 扩容批 | 同首批型号，同 fabric 域 | +16 | +128（累计 256） | 【待填，见 C2】 |
| 长期规划 | 同型号 | 递增至百卡～千卡级 | — | 按需预约 |

**扩容是硬需求，不是选项。** 供应商方案中必须说明：首批交付时**为扩容预留的
fabric 端口、机柜位、供电容量**分别是多少，以及在不停机、不迁移、不降低跨节点
通信性能的前提下，最大可就地扩容到多少卡。

> ⚠️ **扩容必须在同一个无收敛 fabric 域内。** 如果扩容节点被放到另一个 fabric 域、
> 或与首批节点之间存在收敛比，则 128→256 卡的跨节点 AllReduce 性能会显著劣化，
> 这种扩容对我方无价值。请在应答中明确承诺同域扩容的上限卡数。

### 2.2 NVLink：8 卡单域（硬性否决项）

**每个节点的 8 颗 GPU 必须处于同一个 NVLink 域内，通过 NVSwitch 全互联。**

验收判据（我方逐台实测，见附录 A §4）：

- `nvidia-smi topo -m` 中 **56 个 GPU 对（8×7）全部显示 `NV18`**，不允许出现
  `PIX` / `PXB` / `PHB` / `SYS` / `NODE`。
- 每卡 NVLink 链路数 = **18 条**，全部 `Active`。
- `nvidia-smi nvlink -e` 的 CRC / Replay 错误计数 = 0。
- P2P 单向带宽：B 系列 ≥ 750 GB/s，H 系列 ≥ 345 GB/s；P2P 延迟 ≤ 5 μs。
- 8 卡 NCCL AllReduce Bus BW：B 系列 ≥ 800 GB/s，H 系列 ≥ 350 GB/s。
- Fabric Manager 服务处于 `active (running)` 状态，NVSwitch 全部在位无降级。

**明确拒收以下形态**，出现任意一种该节点判定不通过、不起租：

1. **PCIe 版 GPU + NVLink Bridge** —— 只能两两互联，8 卡张量并行会退化到走 PCIe。
2. **4+4 拆域**或任何非 8 卡单域的 NVLink 分区。
3. **NVSwitch 故障降级**运行（部分链路不通但系统仍可启动）。
4. **Fabric Manager 未启动**或版本与驱动不匹配，导致 NVLink 未建链。
5. **MIG 已开启**或 GPU 被虚拟化切分（vGPU / 直通给多租户）。我方要求整机独占。

> 为什么单列这一条：以上几种情况在跑单卡推理或 `nvidia-smi` 看卡数时**完全看不出来**，
> 只有在 8 卡张量并行 / FSDP 时才暴露，那时候机器已经起租了。

`【应答】` 请提供一台样机的 `nvidia-smi topo -m` 完整输出、`nvidia-smi nvlink -s` 输出，
以及 8 卡 `all_reduce_perf` 的实测结果截图或日志。

### 2.3 集群网络

#### 2.3.1 组网架构

| 项目 | 要求 |
|---|---|
| 计算网络 | InfiniBand 或 RoCE v2 均可，**须明确说明是哪一种**及交换机型号 |
| 配比 | **GPU : 计算网卡 = 1 : 1**，不接受 2:1、4:1 |
| 收敛比 | **1:1 无收敛**（full fat-tree / rail-optimized） |
| 拓扑 | 轨道优化（rail-optimized）：节点内第 i 张网卡接入第 i 组 leaf |
| PCIe | 每张计算网卡独占 PCIe Gen5 x16（400G）/ **Gen6 x16（800G）** |
| GPU-NIC 亲和 | `nvidia-smi topo -m` 中 GPU 与其配对网卡为 `PIX` 或 `PXB`，**不得为 `SYS`** |
| GPUDirect RDMA | 必须可用（`nvidia_peermem` 已加载或 dmabuf 路径打通），ACS 关闭 |
| 存储网络 | **独立物理网络**，≥ 2 × 100 GbE |
| 管理网络 | 独立，含带外 BMC |

> ⚠️ **两个常见的隐性缩水，请在应答中正面回应：**
> 1. **800G 网卡插在 PCIe Gen5 槽上。** Gen5 x16 单向约 504 Gb/s，CX-8 的 800G 口
>    在 Gen5 槽上永远跑不到线速。B300 平台必须是 Gen6 x16。
> 2. **GPU 与其网卡跨 CPU socket（topo 显示 `SYS`）。** GDR 流量要绕 UPI，
>    实测带宽和延迟都会明显劣化，而 `ibstat` 看一切正常。

### 2.6 稳定性、掉卡与慢节点

原需求"提供故障自动恢复机制"过于笼统，无法验收，本节改为可量化、可举证的条款。

> **本节是本次采购最重要的一节。** 在同步数据并行训练里，集群的实际产出由
> **最慢的那个 rank** 决定，而不是由平均值决定。一台节点慢 10%，整个 128 卡
> 集群就慢 10%；一张卡掉了，8 卡张量并行的整台机器就用不了。
> 这两类故障的共同特点是：**机器还在、能登录、监控全绿、传统 SLA 一分钱不赔。**
> 所以必须单独定义、单独计量、单独约定赔偿。

#### 2.6.3 慢节点（straggler）

**慢节点是本次采购最容易被忽略、也最难事后追责的问题。**
它的典型表现是：所有绝对指标都达标、验收也能通过、监控利用率 100%，
但这台机器就是比同批次其他机器慢，拖慢整个训练。

常见成因（供应商需说明各自的检测手段）：

| 成因 | 特征 | 检测手段 |
|---|---|---|
| 热降频 | 机柜位置差、进风温度高、风扇故障、导热硅脂不良 | `clocks_throttle_reasons` 含 SW/HW thermal slowdown |
| 功率封顶 | 机柜供电不足或 power limit 被下调 | throttle reason 含 power cap；`nvidia-smi -q -d POWER` |
| PCIe 降级 | 链路跑在 Gen4 或 x8 而非 Gen5/6 x16 | `nvidia-smi -q` 的 link gen/width；`lspci -vv` LnkSta |
| NVLink 部分降级 | 链路数不足 18 但系统不报错 | `nvidia-smi nvlink -s` |
| 网卡问题 | 口速协商到低速、跨 socket（topo 显示 `SYS`）、PFC 频繁 pause | `ethtool`/`ibstat`、topo -m、PFC 计数 |
| CPU / NUMA | 频率被限、NUMA 绑定错、dataloader 抢不到核 | `turbostat`、numactl 绑定检查 |
| ECC 重试 | 大量可纠错 ECC 导致隐性重试 | ECC corrected 计数增量 |
| 存储侧饿死 | 该节点存储路径慢，dataloader 供不上数据 | 单节点存储带宽实测 |

**慢节点的认定标准（我方口径，写入合同）：**

> 在同一批次、同一测试条件下，某节点的基准性能**低于该批次中位数 10% 以上**，
> 即认定为慢节点。
>
> 基准测试项：单机 8 卡 NCCL AllReduce Bus BW、gpu_burn 吞吐、
> H2D/D2H 带宽、单节点存储读带宽。任意一项触发即成立。
>
> 依据：我方验收工具链的同批次横向比对（`compare_batch.sh`），
> ≥95% 中位数为通过、90%～95% 为复测、< 90% 判不通过。

#### 2.6.4 故障类型覆盖与自动恢复

自动恢复机制需覆盖以下故障类型，请逐项说明检测手段与处置动作：

1. **GPU XID 错误 / ECC 不可纠错** —— 自动隔离该卡与该节点
2. **NCCL 通信超时 / hang** —— 自动识别是哪个 rank 掉队，而不是简单重启全部
3. **IB / RoCE 链路 down、PFC 风暴**
4. **NVLink CRC 错误累积**
5. **节点宕机 / 掉电**
6. **慢节点** —— 自动从可用池中摘除，不再分配新任务
7. **静默数据损坏（SDC）** —— 计算结果错误但无任何报错。请说明是否有定期
   DCGM diag -r 3/4 巡检或数值校验机制。**这是千卡集群最难查的一类故障。**

恢复流程需说明：是否自动从最近 checkpoint 拉起、是否自动替换为热备节点、
是否需要人工介入、通知渠道是什么。

`【应答】` 请提供贵司同规模集群近 3 个月的**真实故障统计**：故障次数、
类型分布、平均恢复时长、**掉卡次数与更换耗时**、**慢节点发现次数与处置耗时**、
Goodput 实际值。

### 5.2 验收原则

## 6. 服务等级协议（SLA）

> 通用 SLA 只考核"机器是否可用"，而我方的三类主要损失里有两类不体现为不可用：
> **掉卡**（机器还在，8 卡并行已经废了）和**慢节点**（机器全绿，只是慢）。
> 因此本节按**三个独立指标**分别考核，任一不达标独立触发赔偿，**不相互抵扣**。

### 6.1 三项 SLA 指标

| # | 指标 | 承诺值 | 统计周期 |
|---|---|---|---|
| SLA-1 | 集群可用率 | ≥ 99.5% | 自然月 |
| SLA-2 | 有效训练时间占比（Goodput） | ≥ 95% | 自然月 |
| SLA-3 | 慢节点比例 | ≤ 5% 且单台处置 ≤ 48 h | 自然月 |

**计算公式（写入合同，不接受模糊表述）：**

```
可用率 = (在租节点·小时总数 − 不可用节点·小时数) / 在租节点·小时总数

  其中「不可用」包含：节点宕机、无法登录、掉卡（按 2.6.2 的口径，
  掉任意 1 卡即该节点整机不可用）、网络中断、存储不可读写、
  以及超出约定窗口的计划内维护。

Goodput = (T总 − T中断 − T回退 − T慢节点折算) / T总

  T中断     = 因平台故障导致训练进程终止到重新拉起的时长
  T回退     = 从上次 checkpoint 重跑所损失的时长
  T慢节点折算 = Σ (慢节点存续时长 × 该节点相对中位数的性能差值百分比)
              例：一台节点慢 15%、存续 100 小时 → 折算 15 节点·小时
```

`【应答】` 是否接受上述三项指标与计算公式？如有异议请给出贵司版本的完整公式。
